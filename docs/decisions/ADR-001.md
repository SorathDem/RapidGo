
# ADR-001: Selección del topic, clave y particiones de Kafka

- **Estado:** Aceptado para la configuración inicial.
- **Fecha:** 2026-10-21.
- **Proyecto:** RapidGo — Equipo 6, Variante 8.
- **Responsable:** P2 — Arquitectura.

## 1. Contexto

RapidGo necesita procesar eventos de telemetría y mantenimiento de sus vehículos. Cada evento puede incluir el identificador del vehículo, kilometraje, temperatura del motor y código de falla.

La solución necesita recibir los eventos, distribuirlos para su procesamiento y conservar la relación entre los registros de un mismo vehículo.

## 2. Decisión

Se establece la siguiente configuración inicial:

| Elemento | Decisión |
|---|---|
| Topic | `rapidgo.fleet.mantenimiento.v1` |
| Clave del mensaje | `vehicle_id` |
| Número de particiones | 4 |
| Factor de replicación | 1 en el entorno local |

## 3. Justificación

### Topic

Se utiliza `rapidgo.fleet.mantenimiento.v1` porque identifica el proyecto, el dominio de mantenimiento de flota y la versión inicial del flujo de eventos.

El sufijo `v1` permite identificar la primera versión del contrato de eventos y facilita distinguirla de posibles versiones futuras.

### Clave del mensaje

Se selecciona `vehicle_id` como clave para que los eventos de un mismo vehículo se asignen a la misma partición con la configuración de particionado utilizada.

Esto permite conservar el orden de los eventos de un vehículo dentro de esa partición, aspecto importante para analizar la evolución del kilometraje y las fallas.

### Particiones

Se seleccionan cuatro particiones para disponer de varias unidades de paralelismo durante la demostración local y permitir que los consumidores procesen diferentes grupos de vehículos.

La cantidad de particiones es una decisión inicial para el proyecto académico y puede revisarse si cambia el volumen de eventos o la capacidad de procesamiento.

### Factor de replicación

Se utiliza un factor de replicación de 1 porque el entorno local tiene un único broker de Kafka. Esta configuración es suficiente para las pruebas, pero no ofrece tolerancia a la pérdida del broker.

## 4. Alternativas consideradas

- **Una sola partición:** simplifica la configuración, pero limita el paralelismo.
- **Tres particiones:** es una alternativa válida, pero se seleccionaron cuatro para la configuración definida en el plan.
- **Usar una clave distinta de `vehicle_id`:** podría repartir los mensajes de otra manera y no garantizaría que los eventos de un mismo vehículo se agrupen en la misma partición.

## 5. Evidencia de la decisión

La configuración se verificó mediante la consulta de metadatos del topic y una prueba de productor y consumidor.

En la prueba inicial se enviaron tres mensajes:
- Dos mensajes con clave `VAN-017`, recibidos en la partición 1.
- Un mensaje con clave `VAN-018`, recibido en la partición 0.

El consumidor procesó los tres mensajes. La terminación por tiempo de espera se produjo después de no recibir más eventos.

La salida completa de la prueba debe conservarse en `docs/evidencias/` si esos archivos están disponibles en el repositorio.

## 6. Consecuencias

- Los eventos se organizan por vehículo mediante `vehicle_id`.
- Las cuatro particiones permiten paralelismo entre grupos de vehículos.
- El factor de replicación 1 es apropiado para el entorno local, pero no para una configuración que requiera alta disponibilidad.
- Los consumidores deben utilizar el mismo contrato de eventos acordado por el equipo.
